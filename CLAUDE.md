# CLAUDE.md — Master Workflow Instructions

> Version: 4.0
> This is the single source of behavioural truth.
> If any other file conflicts with this file, this file wins.

## 0. Authority Map

Use the files by authority, not by convenience:
1. `CLAUDE.md` — rules, invariants, hard gates
2. `AGENTS.md` — role procedures only
3. `PROJECT.md` — current project state and indexes
4. `TASKS.md` — task content blocks only
5. `TOOLS.md` — tool permissions and external-path allowlist
6. `MEMORY.md` / `ENTITIES.md` / `USER.md` / `WORKING.md` / `LOG.md` — data
7. `WORKFLOW.md` and `SOUL.md` — explanatory/reference only

`WORKFLOW.md` is illustrative. `SOUL.md` sets tone only. Neither file grants permissions or overrides rules.

## 1. Core Invariants

1. Task status lives only in `PROJECT.md` TASK INDEX.
2. Subtask status lives only in `PROJECT.md` SUBTASK INDEX.
3. `TASKS.md` never owns status.
4. Project `status:` is derived from the TASK INDEX. Agents do not hand-edit it except during initial `SCOPING`.
5. Raw secrets never appear in repo files. `ENTITIES.md` stores metadata and `secret_ref` / `path_ref` only.
6. Builders and Reviewers use `WORKING.md` keys at `TASK-NNN/subtask-NN` scope by default.
7. Before work starts, and after any structural state change, run `python3 scripts/repo_doctor.py --check`.
8. If `repo_doctor.py` reports an invariant failure, stop and set `NEEDS_HUMAN` unless the failure is a purely mechanical sync issue that `--sync-project` fixes.
9. If the request is ambiguous, ask. If it is clear and certainty ≥ 95%, execute without asking for confirmation.

## 2. Approval Model

Approval is two-step and version-bound.

Lifecycle:
`SCOPING → CLARIFYING → AWAITING_SPEC_APPROVAL → PLANNING → AWAITING_PLAN_APPROVAL → APPROVED → IN_PROGRESS → REVIEW → DONE`

Projects start at SCOPING. Tasks start at CLARIFYING.

At any point: `BLOCKED | NEEDS_HUMAN`

Rules:
- No task may move from `CLARIFYING` to `PLANNING` without a valid spec approval line.
- No task may move from `PLANNING` to `APPROVED` without a valid plan approval line.
- Every approval must bind to the exact artifact version and fingerprint present in `TASKS.md`.
- Editing an approved SPEC or PLAN invalidates that approval immediately.

Required approval line formats:
- `STATUS_CHANGE: SPEC_APPROVED — YYYY-MM-DD — SPEC-vN — sha256:<fingerprint>`
- `STATUS_CHANGE: PLAN_APPROVED — YYYY-MM-DD — PLAN-vN — sha256:<fingerprint>`

Legacy v3 tasks may remain in the archive with a migration note, but all new or reopened tasks must use the v4 format.

## 3. Credential & Entity Protocol

When Thomas provides any credential, token, password, key, endpoint, or named service fact:
1. Stop the current task.
2. Write or update the corresponding block in `ENTITIES.md`.
3. Store only metadata plus `secret_ref`, `path_ref`, or retrieval instructions.
4. Never write raw secret values to `ENTITIES.md`, `LOG.md`, `TASKS.md`, `MEMORY.md`, or source files.
5. Log the entity write.
6. Confirm: `Saved to ENTITIES.md. Continuing.`

If a secret is stale or invalid:
- Set `confidence: LOW`
- Add `invalidated_at:`
- Set status to `NEEDS_HUMAN`
- Do not retry with the same invalid secret

`USER.md` is the canonical human profile. `ENTITIES.md` may reference the human, but does not duplicate preference data.

## 4. Concurrency, Atomic Writes, and Derived State

Before writing any shared `.md` file:
1. Read fresh from disk.
2. Compare against the version seen at boot.
3. Merge if different sections changed.
4. If the same line changed, later timestamp wins and the second writer appends its delta.
5. Write atomically.

Derived state rules:
- `PROJECT.md` project status is generated from task rows.
- File size monitor rows in `PROJECT.md` are generated by `scripts/repo_doctor.py --sync-project`.
- `WORKING.md` task-level keys are reserved for the Planner phase.
- Builder / Reviewer phases must use subtask keys to avoid parallel overwrite collisions.

## 5. Logging and Working Memory

`LOG.md` is append-only. Format: `[YYYY-MM-DDTHH:MM:SS] [AGENT-ID] [TASK-ID[/subtask-NN]] LEVEL EVENT=<event-type> — message`. Full event type list in **WORKFLOW.md §Logging Reference**.

Required events: `CLAIM`, `STATUS_CHANGE`, `HEARTBEAT`, `REVIEW_PASS`, `REVIEW_FAIL`, `RECLAIM`, `SCOPE_INVALIDATION`, `MEMORY_WRITE`, `ENTITY_WRITE`, `SYNC`, `DEPLOY`, `SMOKE_PASS`, `SMOKE_FAIL`, `VISUAL_APPROVED`, `VISUAL_REJECTED`, `GATE_FAIL`, `AUTONOMY_OVERRIDE`.

Heartbeat: every 30 min → single combined LOG entry confirming liveness and referencing current WORKING.md state. No separate WORKING.md write between heartbeats.
**LOG.md auto-archive at 500 lines**: if LOG.md exceeds 500 lines, move the oldest 100 entries to `archives/LOG.archive.md`.

Staleness: 30+ min inactive → any agent may reclaim. Resume from `WORKING.md`; otherwise reconstruct from `LOG.md` + `TASKS.md`.

### Atomic Write Simplification
For append-only operations (LOG.md, HEARTBEAT), write directly — no read-compare-merge cycle needed. For shared file updates (TASKS.md, PROJECT.md), always read fresh first.

## 6. Boot Sequence

1. **Read all foundation files in parallel (single batch):** `CLAUDE.md`, `PROJECT.md`, `TOOLS.md`, `MEMORY.md`, `ENTITIES.md`, `USER.md`, `CAPABILITIES.md`.
2. Read `IDENTITY.md` if present. It is optional metadata; a blank identity is not a blocking error.
3. Read the last 30 lines of `LOG.md`.
4. Read the last 50 lines of `SESSION.md` — this is the ephemeral session log of what the previous session just fixed or discovered. **Truncate if >200 lines** (archive oldest entries).
5. Read `CAPABILITIES.md` — this is the live capability registry. Check it BEFORE declaring any capability unavailable.
6. Read the specific task or subtask block in `TASKS.md`. Determine active role (Planner/Builder/Reviewer) from task status.
7. Read `WORKING.md` for resumable state.
8. **Lazy-load only the active role section from `AGENTS.md`** — do not load all three roles. If no task is claimed yet, skip AGENTS.md entirely.
9. **GATE 0 — Structural Validator:** Run `python3 scripts/repo_doctor.py --check 2>/dev/null`. Output suppressed unless errors. If it fails, stop. Do not proceed until the repo is clean.
10. If you claim work, create or update your `WORKING.md` keyed block immediately.
11. Begin heartbeat cadence.

After maintenance, compression, or archive moves:
- Run `python3 scripts/repo_doctor.py --sync-project`.
- Review stale credentials and line-count pressure before starting new decomposition work.

## 6b. Process Enforcement Anchors

The validator runs at every structural transition point. See **WORKFLOW.md §Enforcement Anchors** for the full trigger/action/failure table. Summary:
- Agent boots → `repo_doctor --check` (stop if fails)
- Claims, status writes, archive actions → `repo_doctor --sync-project` + `--check`
- Builder pre-REVIEW, Reviewer pre-DONE → sync + check (BLOCKED if errors)
- Every ~30 min heartbeat → silent check; log `GATE_FAIL gate=0` if errors (GATE 0 removed — runs only at boot + phase transitions per §6b)

Mutual enforcement: any agent that detects another agent's structural drift without a corrective log must log `GATE_FAIL gate=0 reason=structural-drift-detected` and BLOCK the affected task.

## 7. Role Mapping

- **Planner**: (Status: `SCOPING`, `CLARIFYING`, `PLANNING`)
  - Decomposes project into `TASKS.md`.
  - Produces both SPEC and PLAN.
  - Obtains human approval for both.
  - **Enforcement**: Run `repo_doctor --check` before presenting SPEC and before presenting PLAN.

- **Builder**: (Status: `APPROVED`, `IN_PROGRESS`)
  - Implements code and configuration.
  - Acts autonomously on any service with a stored credential in `ENTITIES.md`.
  - Runs initial Quality Gates 1–7.
  - **Enforcement**: Run `repo_doctor --sync-project` then `--check` after Gates 1–7 and before moving to REVIEW. BLOCKED if errors.

- **Reviewer**: (Status: `REVIEW`)
  - Performs Independent Re-Statement Protocol.
  - Re-runs all gates and performs Smoke Checks.
  - Promotes tasks to `DONE`.
  - **Enforcement**: Run `repo_doctor --sync-project` then `--check` before promoting to DONE. BLOCKED if errors.

**Independent Re-Statement Protocol:** Before gates, write scope / expected output / gate criteria in REVIEW block. Contradicts SPEC/PLAN → log `SCOPE_INVALIDATION` and stop.

## 8. Quality Gates

Gate numbers start at 0. All mandatory. No task advances past a failing gate. Detailed descriptions in **WORKFLOW.md §Quality Gates Reference**.

- **GATE 0**: `repo_doctor --check` passes (all agents, all phases)
- **GATE 1**: Tests pass (`test_command`)
- **GATE 2**: Build passes (`build_command`) if defined
- **GATE 3**: Coverage meets `coverage_gate` if not `none`
- **GATE 4**: Lint passes (`lint_command`)
- **GATE 5**: E2E passes (`e2e_command`) — N/A if `e2e_command` is not defined in `PROJECT.md`
- **GATE 6**: Visual regression passes if `visual_regression_command` is defined; diffs require `VISUAL_APPROVED` log event
- **GATE 7**: A11y passes (`a11y_command`) — N/A if `a11y_command` is not defined; zero critical/serious violations required
- **GATE 8**: `smoke_url_ref` updated in `PROJECT.md` — N/A if the project has no deployed URL
- **GATE 9**: Independent re-run of Gates 1–7, smoke check, structured REVIEW block, memory capture

## 9. Autonomy Rule

Once a credential is stored in `ENTITIES.md`, the agent acts autonomously — do not ask Thomas to click or configure things the credentials already cover. Full rules in **WORKFLOW.md §Autonomy Reference**.

- `confidence: HIGH` → act, log
- `confidence: MEDIUM` → act, log WARN; set `NEEDS_HUMAN` on failure
- `confidence: LOW` or `invalidated_at:` → do NOT act; set `NEEDS_HUMAN` with exact gap

Exceptions requiring human action: billing changes, DNS changes (no API key), OAuth consent, destructive irreversible actions. `AUTONOMY_OVERRIDE` events must log the justification.

## 10. Tool Preference: CLI First

When a CLI and an MCP (or other IPC mechanism) both exist for the same tool, prefer the CLI. CLI calls are a single stdin/stdout exchange. MCP round-trips carry schema negotiation and response framing overhead that burns tokens unnecessarily.

Apply this to: git, yt-dlp, gh, vercel, npm, pip, and any tool with a CLI interface. If a needed CLI wrapper does not exist, build one as `scripts/<tool>-cli.py` with structured (JSON) output.

## 11. Scope Change, BLOCKED, and Escalation

Scope change on a task already `APPROVED` or beyond:
1. Set task back to `CLARIFYING`
2. Invalidate downstream tasks to `NEEDS_HUMAN`
3. Log `EVENT=SCOPE_INVALIDATION`
4. Require fresh spec and plan approvals

## 14. BLOCKED and NEEDS_HUMAN

### BLOCKED
Trigger: Same gate failed twice in one session → task enters BLOCKED state.

Required fields:
- `reason:` — exact cause of the block
- `rollback_to:` — last known good status
- `blocked_sessions_count:` — how many sessions have this block
- `gate_failed:` — which gate failed

Resolution: Agent documents corrective action needed. Task stays BLOCKED until Thomas resolves or approves override. Log `STATUS_CHANGE` to `BLOCKED`.

### NEEDS_HUMAN
Trigger: confidence=LOW, invalidated credentials, autonomy override required, third unresolved blocked session.

Required fields:
- `reason:` — gap or blocker requiring human action
- `rollback_to:` — safe restore point
- `blocked_sessions_count:` — how many sessions hit this
- `suggested_resolution:` — if known

Resolution: Thomas takes action. Agent does not retry autonomously. Log `STATUS_CHANGE` to `NEEDS_HUMAN`.

### Mutual enforcement
Any agent that detects BLOCKED drift (task not in valid BLOCKED/NEEDS_HUMAN state) must log `GATE_FAIL gate=0 reason=structural-drift-detected` and BLOCK the affected task until verified.

## 12. Live Capability & Session Memory

### The Problem
Session outcomes are ephemeral — they live in the transcript and get compacted away. The next session starts clean and repeats mistakes the previous session just fixed. This is a lossy unidirectional pipeline: workspace files load at boot, but session discoveries don't write back unless explicitly captured.

### The Fix: Three-Tier Memory System

**HOT — every boot, read always:**
- `CAPABILITIES.md` — live service states, working keys, known broken states. Not optional.
- `WORKING.md` — active task state only (resumable)
- `LOG.md` last 30 lines — audit trail

**WARM — on demand, sparse access:**
- `MEMORY.md` — patterns, decisions, hard-learned lessons
- Only read when: task context explicitly references it, or after a gap >2hrs
- NOT boot-critical — safe to skip on fresh sessions

**COLD — never auto-read:**
- `archives/*` — anything older than 30 days or explicitly archived

---

**SESSION.md (ephemeral, HOT tier)**
- Written DURING the session, not at the end
- Captures: what was just fixed, deployed, broken, or discovered
- Read on every boot: last 50 lines gives recent context
- **Auto-archive at 200 lines**: if SESSION.md exceeds 200 lines, move the oldest 50 entries to `archives/SESSION.archive.md` before continuing
- Entries are promoted to MEMORY.md and CAPABILITIES.md before the session closes

### Mandatory Capture Rules

**Rule 1 — Critical events: write to ALL layers immediately (not just SESSION.md)**
After any of the following events, write to SESSION.md AND promote directly to CAPABILITIES.md/MEMORY.md in the same action — do not defer to end-of-session:
- Cloudflare Workers, Vercel deployment, DNS changes, API key rotation
- New service wired up or reconfigured
- A capability that was broken is now working
- A capability that was working is now broken (and why)

**Rule 2 — SESSION.md: track promotion state per entry**
Format: `[SYNCED:capabilities|memory]` suffix on entries that have been promoted. Unsynchronized entries (no suffix) must be promoted before the session closes or on the next boot of any agent.

**Rule 3 — On any boot: drain unsynchronized SESSION.md entries first**
Before starting new work, scan SESSION.md for entries without `[SYNCED:` — promote them now. This is a structural dependency, not optional cleanup.

**Rule 4 — Before declaring "I can't do X" → check CAPABILITIES.md first**
If the capability is listed as LIVE → verify the failure independently before reporting unavailable
If the capability is listed as BROKEN → report the known broken state with the fix context
If the capability is UNKNOWN → investigate, don't assume unavailable

### Log Events for Memory Writes
- `MEMORY_WRITE` — wrote significant entry to MEMORY.md
- `CAPABILITY_UPDATE` — updated CAPABILITIES.md
- `SESSION_LOG` — appended to SESSION.md

## 13. Archive & Compression Policy

Compression must reduce active working files, not merely move content lower in the same file.

Use companion archive files:
- `archives/MEMORY.archive.md`
- `archives/TASKS.archive.md`

When an active file exceeds 200 lines:
1. Move completed entries or completed task blocks to the companion archive file intact.
2. Leave a stub in the active file with tags and archive pointer.
3. Log the archive move.
4. Run `python3 scripts/repo_doctor.py --sync-project`.

`ENTITIES.md` is never archived.
`SCHEDULES.md` is static and exempt.
